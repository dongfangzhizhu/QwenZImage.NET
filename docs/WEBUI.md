# WebUI — cross-platform manual test console

`src/QwenZImage.NET.WebUI` is an optional **ASP.NET Core Minimal API** app for
manually testing the library. It reproduces the functional surface of the
original Go WebUI (health, presets, serial job queue, cancel, retry, progress,
output gallery, trash/restore, unload, SSE) entirely in `.NET 10` — **no Go
code and no Go process**. It also exposes the three additive ABI v1 features:
Qwen-Image 2.1 image editing, Z-Image ControlNet Union, and advanced
Qwen-Image 2.1 editing (outpainting / LanPaint / RGBA).

The browser talks to this app; the app calls `QziClient`, which
**directly P/Invokes the in-process `QwenZImageNative` shared library** via the
`qzi` C ABI. There is exactly one transport, no secondary service, no HTTP or
JSON hop between the app and the engine, and no switch to an external server.
The model pack directories come from `QwenZImage.config.json`.

It is a **test console, not the shipping SDK**. It is not packed into the
NuGet package (`IsPackable=false`); the NuGet deliverable is the managed
library plus its two platform native runtimes.

```
browser ──HTTP + SSE──▶ QwenZImage.NET.WebUI (ASP.NET Core, :7860)
                            │  QziGenerationQueue (Channels, single reader)
                            │  WebUiEngine → QziClient (LibraryImport)
                            ▼
                          QwenZImageNative.dll / libQwenZImageNative.so
                            │  qzi.c: validation · single-flight · progress
                            ▼
                          qzi_backend
                            ├─ qzi_stub.c             → noise (reference build)
                            └─ qzi_engine_backend.c   → engine/ C/CUDA (real build)
                                      ▲
                          QwenZImage.config.json (model pack paths)
```

## Run it

Prerequisites: .NET 10 SDK and a built native library (see the root README).
On Windows the library is `QwenZImageNative.dll`, on Linux
`libQwenZImageNative.so`.

> **The commands below start the noise backend.** They are for GPU-free UI and
> API testing only. To generate real images, see
> [Real images: select the CUDA backend](#real-images-select-the-cuda-backend)
> — a CUDA build has to be *selected*, not just built.

```bash
# Windows (PowerShell) — reference backend, no GPU needed
.\scripts\build-native.ps1
dotnet run --project src\QwenZImage.NET.WebUI -c Release

# Linux — reference backend, no GPU needed
bash scripts/build-native-linux.sh
dotnet run --project src/QwenZImage.NET.WebUI -c Release
```

Then open <http://127.0.0.1:7860/>. For a deployable directory (contains
`wwwroot/` plus both staged native runtimes, so no `QZI_NATIVE_LIBRARY` is
needed):

```bash
dotnet publish src/QwenZImage.NET.WebUI -c Release -o artifacts/webui-publish
dotnet artifacts/webui-publish/QwenZImage.NET.WebUI.dll
```

The app falls back to its own directory for static assets when the launch
directory has no `wwwroot/`, so the published build can be started from any
working directory. User data (model weights, outputs) still resolves relative
to the launch directory.

Override the listen address with `QZI_WEBUI_URLS` or the standard `--urls` /
`ASPNETCORE_URLS` (command line always wins):

```bash
QZI_WEBUI_URLS=http://0.0.0.0:8080 dotnet run --project src/QwenZImage.NET.WebUI -c Release
```

A local `Properties/launchSettings.json` (auto-generated by some IDEs) takes
precedence over `QZI_WEBUI_URLS` and picks random dev ports. Pass
`--no-launch-profile` to ignore it, which is what CI-style smoke tests should
do.

> Binding to a non-loopback address exposes the console to your network. It is
> intended for local manual testing; there is no authentication.

## Real images: select the CUDA backend

The **default** native build (`QZI_WITH_CUDA_ENGINE=OFF`) links
`native/src/qzi_stub.c`, a deterministic reference backend: its `make_rgb()`
writes pseudo-random pixels and its `dit` loop only advances a progress bar.
**Matching the `steps` of the original Go version cannot fix that** — no
diffusion happens at all. The yellow banner in the UI says so explicitly, the
health pill reads `reference backend (noise)`, and `/api/health` returns
`engine.reference_backend: true`.

### One command (recommended)

```powershell
.\scripts\start-webui-cuda.ps1          # Windows
```
```bash
bash scripts/start-webui-cuda.sh        # Linux
```

The script points `QZI_NATIVE_LIBRARY` at the `-cuda` artefact and sets
`QZI_REQUIRE_REAL_BACKEND=1`, so the WebUI reports `ok=false` / returns HTTP
503 instead of ever serving a noise image. It deliberately does **not** write
into `artifacts/runtimes/<rid>/native/` — that tree is what `dotnet pack` puts
into the NuGet package and must stay GPU-free.

### Why a CUDA build alone is not enough

Three separate things can leave you looking at noise on a machine that already
has a perfectly working CUDA build:

1. **Not selected.** The real build lands in
   `artifacts/native/Windows-AMD64-cuda/` (Linux: `Linux-x86_64-cuda/`), while
   the app loads the bundled `QwenZImageNative.dll` by default. Building is
   step 1; selecting with `QZI_NATIVE_LIBRARY` is step 2.
2. **Staging was reverted.** `scripts/build-native-cuda.bat` stages the CUDA
   library into `artifacts/runtimes/<rid>/native/`, but running
   `scripts/stage-native.ps1` / `.sh` afterwards — which the GPU-free test and
   `dotnet pack` workflow does — restores the ~100 KB reference library there.
   The WebUI project copies native libraries from that directory, so plain
   `dotnet run` silently goes back to noise. This is exactly why the launcher
   sets `QZI_NATIVE_LIBRARY` rather than relying on staging.
3. **Load failed silently.** Previously a missing dependency (cuBLAS / cudart /
   OpenMP) made the loader fall through to the bundled stub. An explicitly
   selected library is now authoritative: a missing or unloadable file throws
   `DllNotFoundException` naming the path and the dependency hint. No image is
   produced at all instead of a plausible-looking noise image.

The WebUI also **auto-detects** a local `-cuda` build when
`QZI_NATIVE_LIBRARY` is unset, so plain
`dotnet run --project src/QwenZImage.NET.WebUI -c Release` on a development
checkout that has built the CUDA engine now produces real images. CI and NuGet
consumers have no `artifacts/native/*-cuda/` tree and keep the reference
backend. Set `QZI_WEBUI_NATIVE=reference` to force the stub for a GPU-free
smoke test.

### Build and select manually

Rebuild the **same library name** with the vendored C/CUDA engine linked in.
The managed assembly, the WebUI and every API call stay unchanged:

```bash
# Windows — script loads vcvars64 automatically; argument is the CUDA SM arch
scripts\build-native-cuda.bat 89          # RTX 4090 = 89, GB10 = 121
# Linux
bash scripts/build-native-cuda.sh 89

# Point the WebUI at the CUDA artefact and at your model packs
export QZI_NATIVE_LIBRARY=/path/to/artifacts/native/Linux-x86_64-cuda/libQwenZImageNative.so
export QZI_CONFIG=/path/to/QwenZImage.config.json
dotnet run --project src/QwenZImage.NET.WebUI -c Release
```

On Windows PowerShell:

```powershell
$env:QZI_NATIVE_LIBRARY = 'D:\...\Windows-AMD64-cuda\QwenZImageNative.dll'
$env:QZI_CONFIG = 'D:\...\QwenZImage.config.json'
dotnet run --project src\QwenZImage.NET.WebUI -c Release
```

`QwenZImage.config.json` is auto-discovered next to the app binary, in the
current directory, up to 8 parent levels above either (so the solution-root
file is found even though `dotnet run` starts the app in the project
directory), then at `~/.config/QwenZImage/config.json`; use `QZI_CONFIG` or
`--config <path>` to be explicit. Its `qwen21_dir`, `zimage_dir`,
`zimage_nunchaku_dir`, `qwen21_lora_dir` and `text_cache_dir` keys point at
model packs you supply yourself — the repository and NuGet package contain no
weights. See [ENGINE_INTEGRATION.md](ENGINE_INTEGRATION.md) for the full
configuration contract and the real backend's call chain.

`/api/health` then reports `transport: "native-pinvoke"`,
`engine.backend: "QwenZImageNative"`, `engine.reference_backend: false`, plus
`native_library` (the exact file loaded) and `native_library_source` (how it
was chosen). The yellow banner disappears. Every other feature (presets,
serial queue, cancel, retry, SSE progress, gallery, trash, unload) is
unchanged.

> **Still seeing noise?** Check `/api/health` first. If
> `engine.reference_backend: true`, read `native_library_source`: it tells you
> whether the stub was chosen because no `-cuda` build was found, because it
> was explicitly forced, or because staging reverted. `QZI_STAGE_CUDA=1` is
> only about what gets packed into the NuGet package — it does not select the
> backend at runtime.

| --- | --- | --- |

| `--config <path>` | — | CLI equivalent of `QZI_CONFIG`, takes precedence |

| `QZI_QWEN21_DIR` / `QZI_ZIMAGE_DIR` | from config | Per-model directory overrides |
| `QZI_ZIMAGE_NUNCHAKU_DIR` / `QZI_QWEN21_LORA_DIR` | from config | Pack directories for LoRA / Nunchaku weights. Read by both `QziConfig` and the native config loader; code-level `QziClientOptions` values are scoped through these variables during engine creation so the engine sees them |
| `QZI_ZIMAGE_CONTROL_DIR` | from config | `zimage_control_dir`: path to the Z-Image Turbo Fun ControlNet Union 2.1 `.safetensors`. Only needed for `zimage-control` jobs; missing → `QZI_ERR_NOT_CONFIGURED` |
| `QZI_MODEL_CACHE` | from config | Text-encoder cache directory |
| `QZI_NATIVE_LIBRARY` | auto-probe | Full path to `QwenZImageNative.dll` / `libQwenZImageNative.so`. When set, it is authoritative — a missing/unloadable file is an error, never a silent fallback to the reference build |
| `QZI_WEBUI_NATIVE` | `auto` | `auto` (detect a local `-cuda` build), `reference` (force the bundled stub), or an explicit library path |
| `QZI_REQUIRE_REAL_BACKEND` | unset | `1` makes the WebUI refuse generation jobs (HTTP 503, `ok=false`) when the reference backend is loaded; set by the one-click launcher scripts |
| `QZI_DEVICE_ID` | `-1` | CUDA device selector passed to the native backend |
| `QZI_PREPROCESS_DIR` | from config | Root of optional WanGP ONNX guide-preprocessor assets (`pose/*.onnx`, `depth*.onnx`, `netG_A_latest.onnx`). Overrides `preprocess_dir`; the native engine ignores it |
| `QZI_HF_MIRROR` | unset (direct `huggingface.co`) | Absolute http(s) mirror base used **only** to rewrite the fixed Hugging Face prefix of model-download URLs from the static WanGP manifest. The repo / path always come from the manifest; callers cannot supply a URL |
| `preprocess_dir` (config key) | unset | Same value stored in `QwenZImage.config.json` (top level or the `windows` / `linux` / `osx` section). Recognised by the strict config parser; read by the WebUI only |
| `device_id` / `thread_count` (config keys) | `-1` / `0` | Auto device / thread count; only in the config file, no env override |

`QziClient` resolves config → `QZI_*` overrides → explicit `QziClientOptions`
(most specific wins). During `qzi_engine_create()` it temporarily publishes the
chosen config path as `QZI_CONFIG` plus the directory overrides, then restores
the process environment, so both sides read the same file without leaking one
client's configuration into another. On Windows the native side reads these
values through `qzi_getenv()` rather than the CRT's stale `getenv()` snapshot;
see [ENGINE_INTEGRATION.md](ENGINE_INTEGRATION.md#作用域发布与多实例隔离).

The WebUI starts even if the native library cannot be loaded: `/api/health`
then reports `ok=false` with the exact error, and `/api/events` emits an
`event: error`. This makes it usable to diagnose a missing runtime or a bad
model path.

### Guide preprocessing (`GET/POST /api/preprocess`)

The **core NuGet library** keeps the C ABI's raw-raster contract: it consumes
the planar RGB `control_image` exactly as supplied and never runs an edge /
pose / depth estimator. Building that raster is an application-layer concern,
so the WebUI owns it. This keeps `QwenZImage.NET` dependency-free while the
WebUI is free to use ONNX Runtime and WanGP's own weights.

Upload an ordinary photograph (PNG / JPEG / WebP — the browser re-encodes it
as an 8-bit PNG) and the WebUI produces the guide that is posted to
`/api/jobs`. Nothing is "used as-is" unless `mode: "raw"` is chosen.

```json
// POST /api/preprocess
{
  "image": "data:image/png;base64,iVBORw0KGgo...",
  "mode": "canny",
  "control_type": "auto",
  "low_threshold": 0.15,
  "high_threshold": 0.35,
  "max_side": 1024
}

// 200 OK
{
  "control_image": "data:image/png;base64,iVBORw0KGgo...",
  "mode": "canny",
  "control_type": "canny",
  "provider": "managed-canny",
  "learned": false,
  "width": 1024,
  "height": 683
}
```

| Field | Rule |
| --- | --- |
| `image` | **Required.** Base64 8-bit PNG or a `data:image/png;base64,...` URL, at most `4096` per side and `2048×2048` pixels total (the native raster limits) |
| `mode` | `auto` (derive from `control_type`), `raw`, `gray`, `canny`, `scribble`, `depth`, `pose`. WanGP guide letters are accepted too: `V`, `C`, `E` / `EV`, `S`, `D` / `DV`, `P` / `PV`; default `auto`. Unknown values → `400` |
| `control_type` | Used only to resolve `mode=auto`. The response always carries the recommended canonical `control_type` — post that alongside `control_image` so the Union weights are not told "pose" while receiving an edge map |
| `low_threshold` / `high_threshold` | Relative Canny hysteresis thresholds, `0 < low < high ≤ 1`, defaults `0.15` / `0.35` |
| `max_side` | Guide downscale limit, `64..4096`, default `1024`. Also capped by the native `2048×2048` pixel budget |

| Mode | WanGP | Provider when no ONNX assets | With WanGP ONNX assets |
| --- | --- | --- | --- |
| `raw` | `V` "Use Z-Image Raw Format" | `raw` | — |
| `gray` | `C` | `managed-gray` | — |
| `canny` | `E` / `EV` | `managed-canny` (Sobel + NMS + hysteresis) | `onnx-wan2gp-contour` |
| `scribble` | `S` | `managed-scribble` (Canny + Zhang-Suen thinning + invert) | `onnx-wan2gp-scribble` |
| `depth` | `D` / `DV` | `managed-depth-proxy` + a `warning` | `onnx-depth-anything-v2` |
| `pose` | `P` / `PV` | `400` with configuration guidance | `onnx-wan2gp-dwpose` (YOLOX-L + DWPose, OpenPose 18-point skeleton) |

The four dependency-free operators need no package and work even on a host
with no GPU or model weights. Learned estimators are discovered lazily from
`QZI_PREPROCESS_DIR` / `preprocess_dir`:

```text
<root>/pose/yolox_l.onnx            # person detector
<root>/pose/dw-ll_ucoco_384.onnx    # DWPose SimCC whole-body keypoints
<root>/**/*depth*.onnx              # Depth Anything V2 ONNX export
<root>/**/netG_A_latest.onnx        # contour / scribble ONNX export
```

WanGP ships `.pth` weights for depth and contour, so export them to ONNX
first; the pose models are already ONNX in a standard WanGP `ckpts` tree.
A missing or failing learned estimator falls back to the managed operator and
returns a `warning`; `pose` is the exception because a classic edge map is not
a pose guide. `GET /api/preprocess` and the `preprocessing` block of
`/api/health` report exactly which assets were found. ONNX sessions are
created on first use and serialised by a single in-process gate.

### Model weights (`GET/POST /api/models*`)

Weight acquisition is a **host-layer** feature. The core NuGet package and the
C ABI still load safetensors from disk exactly as before; nothing in
`src/QwenZImage.NET/` changed for this feature. All URLs come from a static
manifest derived from the local WanGP sources (`defaults/*.json`, the model
handlers and `preprocessing/*/assets.py`), so the browser can only choose file
ids and a variant — it can never submit an arbitrary URL or destination path.

The manifest covers six groups / 32 files:

| Group id | Config key | Contents |
| --- | --- | --- |
| `qwen21` | `qwen21_dir` | Qwen-Image 2.1 DiT (bf16 / int8 variants), VAE + config, scheduler config, Qwen3-VL-8B text tower, tokenizer |
| `qwen21-loras` | `qwen21_lora_dir` | Four LoRA adapters |
| `zimage` | `zimage_dir` | Z-Image Turbo DiT, Qwen3 text encoder, tokenizer / vocab / merges, VAE + config, scheduler config |
| `zimage-nunchaku` | `zimage_nunchaku_dir` | Nunchaku INT4 r32 / r256 checkpoints |
| `zimage-control` | `zimage_control_dir` | Union 2.1 33-channel ControlNet weight |
| `preprocess` | `preprocess_dir` | YOLOX-L / DWPose ONNX, depth and contour assets |

URLs follow WanGP's `build_hf_url(repo_id, *parts)` form:
`https://huggingface.co/<repo>/resolve/main/<path>`, with repos
`DeepBeepMeep/Qwen_image_2`, `DeepBeepMeep/Ideogram4`,
`DeepBeepMeep/Z-Image` and `DeepBeepMeep/Wan2.1`. WanGP does not pin a commit,
so revision follows `main`. Sizes were checked against the Hugging Face API
(32/32 present, 32/32 size matches).

**Endpoints**

```jsonc
// GET /api/models -> snake_case snapshot (excerpt)
{
  "config_path": "D:/.../QwenZImage.config.json",
  "config_platform": "windows",
  "config_target_path": "D:/.../QwenZImage.config.json",
  "config_exists": true,
  "config_overrides": [],
  "mirror": null,              // omitted entirely when QZI_HF_MIRROR is unset
  "default_variant": "int8",
  "paused": false,
  "queue_length": 0,
  "total_bytes": 49710732331,
  "installed_bytes": 46316754706,
  "groups": [
    {
      "id": "qwen21", "config_key": "qwen21_dir",
      "resolved_path": "D:/.../qwen21", "path_source": "config file / CLI override",
      "files": [
        {
          "id": "qwen21.vae_config", "status": "missing",
          "target_path": "D:/.../qwen21/vae_config.json",
          "downloaded_bytes": 0, "total_bytes": 2079, "resume_from": 0,
          "variants": [
            {
              "id": "default", "label": "JSON · 2 KB",
              "url": "https://huggingface.co/DeepBeepMeep/Qwen_image_2/resolve/main/qwen_image_21/vae_config.json",
              "source_url": "...same canonical WanGP URL...",
              "size": 2079, "target_path": "D:/.../qwen21/vae_config.json",
              "curl_command": "...\ncurl -L -C - --retry 3 --fail -o \"...\" \"...\"",
              "recommended": true
            }
          ]
        }
      ]
    }
  ]
}
```

`status` is one of `missing` / `installed` / `downloading` / `paused` / `done` /
`failed` / `queued`; `installed_variant` and `installed_bytes` are detected
from the target file (including WanGP's upstream alias names). A `.qzi-part`
file from an interrupted run is reported as `resume_from`.

```bash
# Queue: ids only. Omit "files" to expand to all missing required files.
curl -sS -X POST http://127.0.0.1:7860/api/models/download \
  -H 'Content-Type: application/json' \
  -d '{"files":["qwen21.vae_config"],"variant":"int8","force":false,"all":false}'
# -> 202 {"queued":1,"skipped":[],"requested":[...],"paused":false,"queue_length":1}

curl -sS -X POST http://127.0.0.1:7860/api/models/control \
  -H 'Content-Type: application/json' -d '{"action":"pause"}'
# actions: pause | resume | reset (needs "file") | reset-all
```

**Resumable transfer.** Each job writes `<target>.qzi-part` and stores the
server ETag in `<target>.qzi-etag`. On resume the downloader sends
`Range: bytes=<part length>-` plus `If-Range: <etag>`; a `206` with
`Content-Range` determines the total, a `200` (server ignored Range) restarts
the file from zero, and a mismatched / truncated body is rejected instead of
being silently appended. Completion validates the length and uses
`File.Move(part, target, overwrite: true)`. `pause` / `resume` / `reset` only
touch these temporary files — finished weights are never deleted.
`QZI_HF_MIRROR` rewrites only the fixed `https://huggingface.co/` prefix;
`source_url` in the snapshot and the manual guide always keep the canonical
WanGP address visible.

**Manual download.** `GET /api/models/manual` returns a Markdown guide with,
for every file, the exact `resolve/main` URL, the absolute destination, a
copy/paste `curl -L -C - --retry 3 --fail -o ...` command (plus a `mkdir -p` /
PowerShell `New-Item` line), the expected size, and a ready-to-paste config
fragment. The Models panel can load, copy and download this file as `.md`.
When a mirror is active, each entry shows both `WanGP source URL` and the
effective mirror URL.

**Config write-back.** `GET /api/models/config` is a **read-only preview** by
default (`applied:false`, no file touched). Only
`POST /api/models/config` with `{"apply":true}` writes: it merges the six
model keys into the current platform section, preserves other platform
sections, `_comment` / `_note` keys and other fields, creates
`QwenZImage.config.json.bak.<yyyyMMdd-HHmmss>` (with an `-i` suffix on
collision), and atomically replaces the file via `.qzi-tmp`. The response
carries `backup_path`, `keys`, `merged_json`, `active_overrides` (any `QZI_*`
environment variable that would override the new file values) and
`restart_required: true` — the native engine reads its config once at
`qzi_engine_create()`, so **restart the WebUI** after applying.

### Request envelope (`POST /api/jobs`)

```json
{
  "model": "qwen21",
  "prompt": "a quiet mountain lake at dawn",
  "width": 1024,
  "height": 1024,
  "seed": 42,
  "tier": "turbo",
  "client": "manual-test"
}
```

`model` accepts `qwen21` (aliases `qwen`, `qwen-image`), `qwen21-edit`
(aliases `qwen21_edit`, `qwen-image-edit`), `zimage`
(aliases `z-image`, `z_image`) or `zimage-control`
(aliases `zimage_control`, `z-image-control`). Qwen21 adds `tier` (`turbo`/`base`);
`lora` and `lora_scale` are valid on **both** tiers, while `steps`,
`guidance` and `negative_prompt` are `base` only. The browser form keeps the
LoRA fields enabled for both tiers and sends them outside the base-only branch;
changing the adapter or its scale reloads the DiT.
Z-Image adds `checkpoint` (`bf16`, `nunchaku`, `nunchaku-r<rank>`).
The full validation rules are in [PARAMETERS.md](PARAMETERS.md); invalid
envelopes fail with `400` **before** any native model loading.

### Image-edit envelope (`POST /api/jobs`)

An envelope enters edit mode either by using `model: "qwen21-edit"` **or** by
adding `reference_image` to a plain `qwen21` request (both spellings are
accepted, so existing scripts only need one extra field). Editing is a
Qwen-Image 2.1 feature: using an edit field with `zimage` fails with `400`.

```json
{
  "model": "qwen21-edit",
  "prompt": "replace the sky with an aurora, keep the mountains",
  "width": 1024,
  "height": 1024,
  "seed": 42,
  "tier": "turbo",
  "client": "manual-test",
  "reference_image": "data:image/png;base64,iVBORw0KGgo...",
  "mask_image": "data:image/png;base64,iVBORw0KGgo...",
  "strength": 0.6,
  "masking_strength": 1.0
}
```

| Field | Rule |
| --- | --- |
| `reference_image` | **Required for edit mode.** Base64 PNG, optionally a `data:image/png;base64,...` URL. The browser canvas re-encodes uploads, so JPEG / WebP files also work. Decoded to planar RGB8; each side `1..4096`, total pixels `≤ 2048×2048` |
| `mask_image` | Optional base64 PNG at the **reference** resolution, one channel. White brush strokes are regenerated, untouched / transparent pixels (0) follow the reference trajectory. `masking_strength` requires it |
| `strength` | Denoising strength `0.05..1.0`, default `0.75`. `1.0` ≈ text-to-image, smaller values stay closer to the reference |
| `masking_strength` | `0.05..1.0`, default `1.0`; only meaningful with `mask_image`, and rejected without it (it would otherwise be silently dropped) |

The reference (and its mask) is centre-crop **cover-fitted** to the output
canvas, so the upload need not match `width`/`height`. Both buffers are
decoded by `QziRasterImage` without any imaging dependency and stay owned by
WebUI for the duration of the synchronous native call. Edit jobs appear in the
job list / gallery with `"edit": true` and `"has_mask": true|false` because
`Qwen21EditOptions` derives from `QwenImageOptions` and the `model` field alone
cannot distinguish them. Adding any advanced field (`margin_*`, `model_mode`,
`rgba`) upgrades the request to `Qwen21EditExOptions` — see the
[advanced-edit envelope](#advanced-edit-envelope-post-apijobs) below; omitting
all of them keeps the ordinary edit export so older native libraries still
work. `/api/health` exposes `supports_image_editing`
(`QziClient.SupportsImageEditing`), which is `false` when the loaded native
library predates the additive editing exports; the UI then disables the
`qwen21-edit` option and switches an already-selected edit mode back to
`qwen21`, so an unsupported job can never be submitted.

### Advanced-edit envelope (`POST /api/jobs`)

An ordinary `qwen21-edit` envelope is upgraded to the third additive ABI v1
increment as soon as **any** advanced field is present. All advanced fields
require `reference_image`; using them with `zimage` still fails with `400`.

```json
{
  "model": "qwen21-edit",
  "prompt": "a quiet mountain lake at dawn",
  "width": 1024,
  "height": 1024,
  "seed": 42,
  "client": "manual-test",
  "reference_image": "data:image/png;base64,iVBORw0KGgo...",
  "mask_image": "data:image/png;base64,iVBORw0KGgo...",
  "margin_top": 128,
  "margin_bottom": 128,
  "margin_left": 128,
  "margin_right": 128,
  "model_mode": 0,
  "rgba": 1
}
```

| Field | Rule |
| --- | --- |
| `margin_top` / `margin_bottom` / `margin_left` / `margin_right` | Optional non-negative integers, **multiples of 32**. They enlarge the **output** canvas: `width` / `height` stay the final size and the reference is cover-fitted into the remaining inner rectangle. All zero / omitted = no outpainting. The inner rectangle must stay at least `32×32` |
| `model_mode` | Optional `0` (masked denoising, default) or `2` / `3` / `4` / `5` (LanPaint with 2 / 5 / 10 / 15 inner Langevin iterations). The numbers are WanGP's combo-box indices, not iteration counts. Requires `mask_image` and is **mutually exclusive** with any nonzero margin; it also forces both strengths to `1.0` |
| `rgba` | Optional `0` (RGB PNG, default) or `1` (RGBA PNG using the VAE decoder's generated 4th channel). Any other value fails with `400` |

`RequestMapper` returns `Qwen21EditExOptions` when `HasAdvancedParameters()` is
true and keeps returning `Qwen21EditOptions` otherwise, so an older native
library without `qzi_generate_qwen21_edit_ex` can still serve ordinary edit
jobs. `/api/health` exposes `supports_advanced_editing`
(`QziClient.SupportsAdvancedEditing`); when `false`, submitting an advanced
job returns `400` with `WebUiCapabilities.AdvancedEditingUnavailable` instead
of failing minutes later inside the queue, and the front-end shows an
"Unavailable" note in the panel. Job / gallery rows additionally carry
`"advanced_edit"`, `"outpaint"` and `"rgba"` badges derived from
`JobDto.AdvancedEditState()`.

The three features need **no new checkpoint** — they are orchestration and
sampling changes on the same 7B Qwen-Image 2.1 weights. Validation rules live
in [PARAMETERS.md](PARAMETERS.md); the C contract is in
[NATIVE_ABI.md](NATIVE_ABI.md).

### ControlNet envelope (`POST /api/jobs`)

An envelope enters ControlNet mode either with `model: "zimage-control"` **or**
by adding `control_image` to a plain `zimage` request. It is the Z-Image
counterpart of edit mode: using an edit field with `zimage-control` (or a
control field with `qwen21`) fails with `400`, and combining the two feature
sets in one envelope is rejected explicitly.

```json
{
  "model": "zimage-control",
  "prompt": "a red fox walking through fresh snow, cinematic light",
  "width": 1024,
  "height": 1024,
  "seed": 42,
  "checkpoint": "bf16",
  "client": "manual-test",
  "control_image": "data:image/png;base64,iVBORw0KGgo...",
  "control_type": "pose",
  "control_scale": 0.65
}
```

| Field | Rule |
| --- | --- |
| `control_image` | **Required for ControlNet mode.** Base64 PNG, optionally a `data:image/png;base64,...` URL. Decoded to planar RGB8; each side `1..4096`, total pixels `≤ 2048×2048`. The core library consumes this raster exactly as supplied ("raw" semantics), but the browser builds it from an ordinary photo (PNG / JPEG / WebP) through `POST /api/preprocess`, so an already-formatted guide is no longer required. Choose preprocessing `mode: "raw"` to pass a ready-made guide through unchanged |
| `control_type` | Optional, `auto` / `pose` / `canny` / `depth` / `scribble` / `raw` (case-insensitive), default `auto`. Descriptive metadata only; it does not change inference. WanGP's weights support all four control types, and `guide_preprocessing = "V"` means the raster is consumed as-is |
| `control_scale` | Optional `0.05..2.0`, `0` / omitted → engine default `0.65` (WanGP Union 2.1 `control_net_weight_alt`). Must be finite |

`control_type` / `control_scale` **without** `control_image` is rejected with
`400` rather than being silently dropped. The control image is centre-crop
cover-fitted to the output canvas, VAE-encoded into a 16-channel latent, and
padded with zero `keep_mask` / `inpaint_latent` planes into the 33-channel
Union 2.x control context. Control jobs appear in the job list / gallery with
`"control": true` and `"has_control": true`. `/api/health` exposes
`supports_controlnet` (`QziClient.SupportsControlNet`); when `false` the UI
disables the `zimage-control` option and switches an already-selected control
mode back to plain `zimage`. Real inference additionally requires
`zimage_control_dir` (or `QZI_ZIMAGE_CONTROL_DIR`); with the reference backend
the request still succeeds but only produces the deterministic byte-comparison
image.

### Inpaint envelope (`POST /api/jobs`)

A fourth additive mode: `model: "zimage-inpaint"`, **or** a ControlNet request
that also carries `mask_image`. Either way both `control_image` and
`mask_image` are required; the request is mapped to `ZImageInpaintOptions`
(`GenerateZImageInpaint`). Editing (qwen21-edit) and inpaint remain mutually
exclusive, just like editing and ControlNet.

```json
{
  "model": "zimage-inpaint",
  "prompt": "a red fox walking through fresh snow, cinematic light",
  "width": 1024,
  "height": 1024,
  "seed": 42,
  "checkpoint": "bf16",
  "client": "manual-test",
  "control_image": "data:image/png;base64,iVBORw0KGgo...",
  "control_type": "raw",
  "control_scale": 0.65,
  "mask_image": "data:image/png;base64,iVBORw0KGgo..."
}
```

| Field | Rule |
| --- | --- |
| `control_image` | **Required.** Same raster rules and `control_type` / `control_scale` semantics as the ControlNet envelope above |
| `mask_image` | **Required.** Base64 single-channel 8-bit PNG (or `data:image/png;base64,...` URL) produced by the brush canvas. WHITE (255) = repaint from the prompt, BLACK (0) = keep the control image. Each side `1..4096`, total pixels `≤ 2048×2048`; dimensions need **not** match `control_image` — both are centre-crop cover-fitted to the output canvas independently |

`mask_image` **without** a `control_image` is treated as a Qwen edit field and
rejected with `400`; with `control_image` it is no longer mistaken for an edit
parameter. Jobs appear in the list / gallery with `"inpaint": true` and
`"has_mask": true` (the redundant `control` badge is suppressed).
`/api/health` exposes `supports_inpaint`; when `false` the UI disables the
`zimage-inpaint` option and falls back to plain `zimage`. Real inference also
requires 33-channel Union v2 / v2.1 weights in `zimage_control_dir`; a 16-channel
v1 pack is rejected by the engine. With the reference backend the request still
succeeds but only produces the deterministic byte-comparison image.

### SSE (`/api/events`)

```
retry: 3000

event: job
data: {"id":1,"state":"running","model":"zimage", ...}

event: progress
data: {"job_id":1,"phase":"Dit","completed":3,"total":8,"fraction":0.375, ...}

: ping
```

`job` events are emitted on every state transition and progress tick. While a
job is running, a matching `progress` event is emitted as well. `phase` is the
`GenerationPhase` enum name (`ModelLoad` / `Text` / `ImageEncode` / `Dit` /
`Vae` / `Encode`); `ImageEncode` appears for edit jobs (VAE-encoding the
reference), ControlNet jobs (VAE-encoding the control image) and inpaint jobs
(two VAE encodes: the control image and the masked source image; the real backend folds them into a single `0/1 → 1/1` progress stage, while the GPU-free reference backend reports two `0/2 → 1/2 → 2/2` stages). The stream sends a comment heartbeat every 15 seconds so proxies
do not close idle connections. `EventSource` reconnects automatically.

## Front-end features

- Model selector, presets filtered by model, prompt / negative prompt, width,
  height (step hint changes 32 ↔ 16), seed with randomiser, tier / steps /
  guidance / LoRA / checkpoint fields with automatic enable-disable rules.
  LoRA + LoRA scale stay enabled on **both** `turbo` and `base` (matching the
  library and C ABI); only steps / guidance / negative prompt are base-only.
- Live job table with state badge, progress bar, elapsed time, cancel / retry.
- Output gallery with lazy thumbnails, multi-select, batch delete, "Undo
  delete" (restore), lightbox, and direct link to the original PNG.
- **Image edit mode** (`qwen21-edit`): upload a reference image (PNG / JPEG /
  WebP, re-encoded by the canvas), preview it, and paint a white brush mask on
  a transparent overlay. Buttons clear the mask, paint it all white, or remove
  the image. `Denoising strength` (default 0.75) and `Masking strength`
  (default 1.00, enabled only when a mask exists) are live sliders. Without a
  painted mask the whole image is edited at the denoising strength; white mask
  pixels are regenerated from the prompt, black ones keep the reference. The
  option is disabled when `/api/health` reports
  `supports_image_editing: false`.
- **Advanced edit panel** (inside `qwen21-edit`): top / bottom / left / right
  outpainting margins (step 32, they **enlarge** the output canvas), a
  `Model mode` selector (masked denoising or LanPaint with 2/5/10/15 inner
  iterations) and an `Output channels` selector (RGB / RGBA). The fields are
  sent only when at least one differs from its default, so an ordinary edit
  job still uses the basic edit export. A note explains that LanPaint needs a
  painted mask and cannot be combined with margins; when `/api/health` reports
  `supports_advanced_editing: false` the panel shows an explicit
  "Unavailable" warning while ordinary editing keeps working. Gallery / job
  rows add `advanced_edit` / `outpaint` / `rgba` badges.
- **ControlNet mode** (`zimage-control`): upload an **ordinary photo**
  (PNG / JPEG / WebP, re-encoded by the canvas as 8-bit PNG). The
  **Guide preprocessing** selector turns it into `canny` (default),
  `scribble`, `depth`, `pose`, `gray` or `raw`, with a `Guide max side`
  slider and a "Re-run preprocessing" button; `auto` derives the operator from
  the selected `control type`. The preview and the value posted to
  `/api/jobs` are always the **generated guide**, never the raw upload. The
  server reports the provider (`managed-*` or `onnx-*`) and any fallback
  warning next to the preview. The core NuGet library stays dependency-free
  and keeps the C ABI's raw-raster contract; only the WebUI runs estimators.
  Also available: the descriptive `control type` (`auto` / `pose` / `canny` /
  `depth` / `scribble` / `raw`) and a live `Control scale` slider (`0..2`,
  default 0.65). Real Union 2.1 weights must be configured via
  `zimage_control_dir`; inpaint mode defaults to `raw` so the photo itself is
  the mask backdrop. Edit mode and ControlNet mode are mutually exclusive;
  the option is disabled when `/api/health` reports
  `supports_controlnet: false`. See [Guide preprocessing](#guide-preprocessing-getpost-apipreprocess).
- **Inpaint mode** (`zimage-inpaint`): a strict superset of ControlNet. It
  reuses the same control-image upload / type / scale controls **and** the
  shared brush mask canvas from edit mode (the control image becomes the mask
  backdrop and sets its resolution); no second image component is introduced.
  White = repaint, black / untouched = keep, and both the control image and a
  painted mask are required before queueing. Gallery / job rows show a single
  `inpaint · mask` badge instead of a redundant `control` badge. The option is
  disabled (and an already-selected inpaint mode falls back to `zimage`) when
  `/api/health` reports `supports_inpaint: false`.
- **Models panel** (full-width, below the job/output area): a live table of
  every weight group with status, resolved target path, size, exact URL and a
  resumable `curl` command. A global variant selector (default `int8`) plus a
  per-file override, `Download required` / `Download everything`, and
  Pause / Resume / Reset partials. Polling is 1.2 s while a transfer is active
  and 12 s when idle. Collapsible details hold the manual download guide
  (load / copy / download `.md`) and the config JSON (preview / copy / apply
  with backup). When `QZI_HF_MIRROR` is set, each row also shows the canonical
  WanGP source URL. See [Model weights](#model-weights-getpost-apimodels).
- Health pill showing resident model / backend (`reference backend (noise)`
  vs `QwenZImageNative`), with `transport`, `config_path` and directories in
  the tooltip, plus an "Unload model" action.
- A yellow banner whenever the noise-only reference backend is active, with
  the exact `-DQZI_WITH_CUDA_ENGINE=ON` build instruction.

## Output safety

Mirrors the Go WebUI rules in `OutputStore`:

- Names must be bare file names: no `/`, `\`, NUL, `.`, `..`, or leading `.`.
- Delete **moves** the file to `<out>/.trash` instead of unlinking it.
- Restore refuses symlinks and, if the original name has been reused, writes
  `<stem>-restored-<i><ext>` rather than overwriting the newer file.
- Only the top-level directory is enumerated; `.trash` is a subdirectory and
  therefore never appears in the gallery.

## Cross-platform notes

- The project targets `net10.0` with `Microsoft.NET.Sdk.Web` and has no
  platform-specific code of its own; the only native library is
  `QwenZImageNative`, resolved by `NativeLibraryLoader`.
- The csproj copies `artifacts/runtimes/{win-x64,linux-x64}/native/*` into
  both build and publish output. That makes the console self-contained on
  Windows and Linux; `QZI_NATIVE_LIBRARY` remains available to override it
  with a locally built CUDA artefact.
- Static assets live in `wwwroot/` and are served by `UseStaticFiles` on both
  Windows and Linux. No Node/npm build step is required.
- CI builds the solution on `ubuntu-latest` and `windows-latest` and runs a
  Linux runtime smoke test against the in-process reference backend, asserting
  `transport == "native-pinvoke"`, a resolved `config_path`, and a completed
  job whose PNG appears in the output gallery. GPU builds are not part of CI.
- On Windows, if the default port is in a system-reserved range, set
  `QZI_WEBUI_URLS` to a free port (for example
  `http://127.0.0.1:51234`).
